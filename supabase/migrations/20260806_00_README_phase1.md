# Profile Architecture V2 — Phase 1 runbook

Database foundation only. **No application code changes in this phase.**
Companion: [`PROFILE_ARCHITECTURE_V2.md`](../../PROFILE_ARCHITECTURE_V2.md).

Migrations in this repo are **hand-pasted into the Supabase SQL editor** — there is no
Supabase CLI wired up. Every file below is idempotent and ends with a `DO $$` verification
block that raises on failure.

---

## Execution order

Run in this exact order. Each file is a single paste. Stop immediately if any raises.

| # | File | What it does | Blast radius |
|---|---|---|---|
| 1 | `20260806_01_profile_types.sql` | Creates `profile_types`, seeds `talent` / `brand` / `agency` | New table only |
| 2 | `20260806_02_profiles_profile_type_id.sql` | Adds `profiles.profile_type_id` + index, backfills from `role` | New nullable column on `profiles` |
| 3 | `20260806_03_profile_sections_fields.sql` | Creates `profile_sections`, `profile_fields` | New tables only |
| 4 | `20260806_04_profile_values_layouts.sql` | Creates `profile_values`, `profile_layouts` | New tables only |
| 5 | `20260806_05_booking_provider_shadow.sql` | Adds 3 shadow columns to `bookings`, backfills, creates `booking_provider_drift` | **New nullable columns on `bookings`** |
| 6 | `20260806_06_dynamic_profile_triggers.sql` | Installs both sync triggers, re-runs backfills | **Triggers on `profiles` and `bookings`** |
| 7 | `20260806_07_dynamic_profile_rls.sql` | RLS policies + grants on the V2 tables | New tables only |
| 8 | `20260806_08_seed_profile_schema.sql` | Seeds sections, fields, layouts | Config rows only |

Files 5 and 6 are the only ones that touch a hot table. Read the header comment in each
before running.

`20260806_99_rollback_profile_architecture_v2.sql` is the DOWN script. **Do not run it on a
normal deploy.**

### Ordering constraints

```
01 ──┬── 02  (profiles FK -> profile_types)
     ├── 03 ── 04  (fields FK -> sections; values FK -> fields)
     └── 05  (bookings.provider_type FK -> profile_types.slug)

02 + 05 ── 06   (triggers need both columns to exist)
03 + 04 ── 07   (policies reference all four tables)
03 + 04 ── 08   (seed needs sections + fields + layouts)
```

`07` and `08` are order-independent relative to each other.

## Post-run acceptance checks

All four must pass before Phase 1 is called done.

```sql
-- 1. Drift invariant. MUST be 0. Wire this into CI.
SELECT count(*) AS must_be_zero FROM public.booking_provider_drift;

-- 2. Every non-admin profile is mapped. MUST be 0.
SELECT count(*) AS must_be_zero
  FROM public.profiles
 WHERE profile_type_id IS NULL AND role::text <> 'admin';

-- 3. Shadow columns agree with the legacy column on every booking. MUST be 0.
SELECT count(*) AS must_be_zero
  FROM public.bookings
 WHERE talent_id IS NOT NULL AND talent_id IS DISTINCT FROM provider_profile_id;

-- 4. The pre-existing world is untouched.
SELECT
  to_regclass('public.talent_profiles') IS NOT NULL AS talent_profiles_ok,
  to_regclass('public.brand_profiles')  IS NOT NULL AS brand_profiles_ok,
  EXISTS (SELECT 1 FROM information_schema.columns
           WHERE table_name='bookings' AND column_name='talent_id') AS talent_id_ok;
```

Then run the manual smoke test at the bottom of `20260806_06`, in a transaction you
`ROLLBACK`: it proves an unmodified legacy `INSERT INTO bookings` still produces correct
shadow columns.

Finally, exercise the real app against the migrated database — no code changed, so
everything must behave identically:

- signup as talent and as brand (checks trigger 1 on the three profile-creation paths)
- send a direct brief, accept it, confirm payment (checks trigger 2)
- admin bookings list and talents list render unchanged

## Rollback strategy

**During Phase 1 — fully reversible.** Nothing in the application reads any of these
objects, so the DOWN script restores the exact pre-Phase-1 state:

```
Run 20260806_99_rollback_profile_architecture_v2.sql
```

It tears down in dependency order — triggers, view, `bookings` shadow columns, V2 tables,
`profiles.profile_type_id`, `profile_types` — and asserts at the end that
`talent_profiles`, `brand_profiles` and `bookings.talent_id` survived intact.

**Partial rollback**, if you need to abort mid-run: run the DOWN script regardless of how far
you got. Every statement is `IF EXISTS`.

**Rolling back only the risky part** (keep the new tables, drop the booking changes):

```sql
DROP TRIGGER IF EXISTS trg_sync_booking_provider ON public.bookings;
DROP FUNCTION IF EXISTS public.sync_booking_provider();
DROP VIEW IF EXISTS public.booking_provider_drift;
ALTER TABLE public.bookings
  DROP COLUMN IF EXISTS provider_user_id,
  DROP COLUMN IF EXISTS provider_profile_id,
  DROP COLUMN IF EXISTS provider_type;
```

**After Phase 2 ships, the DOWN script is no longer safe** — application code will read these
tables by then. From that point, rollback means reverting the application commit first, then
the SQL.

### Data loss profile

| Object | Rollback cost |
|---|---|
| `profile_values` | **Destroys user-entered dynamic data.** Zero rows during Phase 1 — nothing writes to it yet. Export first if that has changed. |
| `profile_sections` / `fields` / `layouts` / `types` | Config only, fully re-seedable by re-running `01` + `08`. |
| `profiles.profile_type_id` | Derived from `role`; re-deriving is one `UPDATE`. |
| `bookings.provider_*` | Derived from `talent_id`; re-deriving is one `UPDATE`. |
| Anything pre-existing | **None.** No pre-existing table, column, constraint, index or policy is modified or dropped in Phase 1. |
